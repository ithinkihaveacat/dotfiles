# Harbor Lifecycle and Unattended Execution

Architecture, execution orchestration, candidate evaluation layers, and
Candidate Acceptance Packets for unattended tasks in taskgo.

## Overview

When an isolated worker executes unattended work in a container or external
environment, systematic preparation, bounded orchestration, and independent
verification are required before any candidate change is accepted:

1. **Self-reported worker claims are untrusted:** A worker claiming completion
   may have introduced subtle regressions, modified out-of-scope files, or
   deleted test assertions.
1. **Raw transcript review wastes engineering attention:** Reading multi-step
   agent trajectories shifts investigation overhead back to humans, destroying
   the efficiency of unattended delegation.
1. **Unbounded execution creates compounding risk:** Unconstrained retry loops
   and loose networking risk billing blowouts, prompt drift, and hallucinated
   workarounds.
1. **Automatic branch integration is rejected:** Candidate patches must be
   independently corroborated on the host and presented in a self-contained
   **Candidate Acceptance Packet** for one-click human sign-off.

The `taskgo harbor` command namespace provides the unified CLI to prepare,
execute, and verify unattended tasks using
[Harbor](https://github.com/harbor-framework/harbor).

## The Four Evaluation Layers

To maintain strict data segregation and clear authority boundaries, candidate
assessment is structured into four distinct layers:

```text
┌───────────────────────────────────────────────────────────────┐
│ Layer A: Worker Assertions (Untrusted)                        │
│ - completion.json, agent trajectory, self-reported status     │
└───────────────────────────────┬───────────────────────────────┘
                                │ (Host verification)
                                ▼
┌───────────────────────────────────────────────────────────────┐
│ Layer B: Independent Verification (Host Rerun)                │
│ - File integrity & SHA-256 digests                            │
│ - Patch applicability (patch --dry-run)                       │
│ - Blast radius / file scope audit (no extraneous edits)       │
│ - Re-execution of repo-native linters, formatters & tests     │
└───────────────────────────────┬───────────────────────────────┘
                                │ (Evaluator check)
                                ▼
┌───────────────────────────────────────────────────────────────┐
│ Layer C: Review Judgments (Semantic Evaluation)               │
│ - Conformance to task prompt, acceptance criteria & sketch    │
│ - Absence of malicious, circumventing, or leaky constructs   │
│ - Categorized findings (BLOCKER / WARN / INFO)                │
└───────────────────────────────┬───────────────────────────────┘
                                │ (Decision packet)
                                ▼
┌───────────────────────────────────────────────────────────────┐
│ Layer D: Human Acceptance Boundary (Integration Authority)    │
│ - Explicit human review of Candidate Acceptance Packet        │
│ - Authority to integrate patch into target branch             │
│ - Authority to advance tracker state (done) in control repo   │
└───────────────────────────────────────────────────────────────┘
```

### Layer A: Worker Assertions (Untrusted)

Artifacts generated by the worker (`completion.json`, process exit codes, step
trajectories) represent subjective claims. Worker assertions are captured solely
for telemetry and debugging; they confer zero integration authority.

### Layer B: Independent Verification (Host Rerun)

Host-side checks run completely outside the worker container:

- **Cryptographic integrity:** SHA-256 hashes of base files, candidate outputs,
  and unified diffs.
- **Clean patch application:** Verifying that `patch --dry-run` applies cleanly
  against the target base revision (`p0` or `p1`).
- **Blast radius & scope constraint:** Auditing modified, added, or deleted
  files against declared task targets. Edits outside declared files trigger an
  immediate failure.
- **Repo-native tool re-execution:** Running authoritative project scripts (such
  as formatters, linters, or test suites) on the host to deterministically
  reproduce worker transformations.

### Layer C: Review Judgments

Synthesizes findings from independent host checks and evaluates candidate
alignment against requirements:

- Did the candidate satisfy stated requirements and acceptance criteria?
- Were task constraints respected (e.g. offline execution, no network egress, no
  new dependencies)?
- Are findings structured with explicit severities (`BLOCKER`, `WARN`, `INFO`)?

### Layer D: Human Acceptance Boundary

Integrating patches into shared repository branches and marking tasks `done` in
`STATUS.md` remains strictly a human prerogative. The system produces a
self-contained **Candidate Acceptance Packet** enabling high-confidence
decisions in seconds.

## Automation Boundaries: What to Automate vs What Remains Human

| Operation                          | Automation Status | Rationale                                                                                |
| :--------------------------------- | :---------------- | :--------------------------------------------------------------------------------------- |
| **Trial packaging & scaffolding**  | **Automated**     | Packages task brief, workspace fixtures, and skill bundles via `harbor prepare`.         |
| **Execution orchestration**        | **Automated**     | Drives Harbor execution with timeouts and network allowlists via `harbor run`.           |
| **Artifact extraction & hashing**  | **Automated**     | Pure mechanical ledger work; zero human judgment required.                               |
| **Patch & syntax verification**    | **Automated**     | Deterministic checks (`patch --dry-run`, JSON/YAML parsers) via `harbor verify`.         |
| **Blast radius & scope check**     | **Automated**     | Fails fast if undeclared files are touched.                                              |
| **Host tool re-execution**         | **Automated**     | Re-executing formatting/linters/tests verifies deterministic behavior.                   |
| **Negative filtering (rejection)** | **Automated**     | Bad patches, syntax errors, or broken tests trigger rejection without user intervention. |
| **Acceptance packet synthesis**    | **Automated**     | Generates self-contained Markdown/JSON packet for rapid review.                          |
| **Advisory review commentary**     | **Automated**     | Evaluates diff against prompt criteria to surface non-obvious issues.                    |
| **Task specification & dispatch**  | **Human**         | Curating goals, constraints, and approving execution/budget.                             |
| **Branch integration & merge**     | **Human**         | Merging into target repositories carries architectural, security, and project risk.      |
| **Tracker lifecycle advancement**  | **Human**         | Marking `done` in `STATUS.md` and `tasks/` commits permanent project history.            |

## Installation and Preflights

### 1. Harbor Tool Installation

Harbor is disposable local runner tooling, installed via `uv tool`:

```bash
uv tool install harbor==0.22.0
```

`taskgo harbor` automatically discovers the Harbor binary across `$PATH`, the
`HARBOR_BIN` environment variable, or local project runtimes (e.g.
`~/.projects/taskgo/.runtime/bin/harbor`).

### 2. Docker Daemon Requirement

The runner orchestrates trials in isolated Docker containers. The Docker daemon
must be running and accessible:

```bash
docker info
```

### 3. API Key Management & Spending Limits

For models requiring API keys (such as `google/gemini-3.6-flash-low`), export
the required key in the invoking environment:

```bash
export GEMINI_API_KEY="your-api-key"
```

> [!IMPORTANT] Live runs execute container trials and make billable model calls.
> Never embed keys into `job.json`, shell scripts, or committed files. Exercise
> hard bounds on attempts, concurrency, and timeouts.

### 4. Preflight Validation

Validate environment readiness and trial configuration offline before launching
live trials:

```bash
# Verify preflight checks (Harbor, Docker daemon, config syntax)
taskgo harbor run ./trial-dir --dry-run

# Print resolved Harbor configuration without starting containers
taskgo harbor run ./trial-dir --print-config
```

## Trial Packaging (`taskgo harbor prepare`)

The `prepare` command creates a self-contained trial bundle ready for Harbor:

```text
trial-package/
├── job.json                   # Single-attempt bounded orchestration config
├── skills/                    # Injected agent skills (e.g. coding-standards)
└── tasks/
    └── <task-slug>/
        ├── task.toml          # Egress allowlist, timeouts, declared output artifacts
        ├── instruction.md     # Task instructions and completion protocol
        └── environment/
            ├── Dockerfile     # Isolated container build recipe
            └── workspace/     # Seed files to be modified in place
```

### Command Usage

```bash
# Package a task from the control repository
taskgo harbor prepare TASK-3A91F -o ./trial --skills coding-standards --workspace ./fixtures

# Package with custom instructions and artifacts
taskgo harbor prepare -o ./trial \
  --task-title "Format configuration" \
  --instruction "Use scripts/json-format to format config.json in place." \
  --workspace ./fixtures \
  --artifacts /app/workspace/config.json \
  --skills coding-standards
```

### Key Packaging Options

- `-o, --output DIR`: Destination directory for the prepared trial package
  (creates directory if absent).
- `--workspace DIR`: Seed files copied into `/app/workspace` in the container.
- `--skills SKILL`: Skills to bundle and mount into `/harbor/skills/<skill>`
  (e.g. `coding-standards`).
- `--artifacts PATH`: Container filepaths to recover upon completion (e.g.
  `/app/workspace/config.json`, `/app/completion.json`).
- `--timeout SEC`: Agent execution timeout (default: `60.0`).
- `--setup-timeout SEC`: Container build/setup timeout (default: `180.0`).
- `--allowed-hosts HOST`: Egress domain allowlist during agent phase (default:
  `generativelanguage.googleapis.com`).
- `--dry-run`: Preview generated files without writing to disk.

## Execution Orchestration (`taskgo harbor run`)

The `run` command executes a prepared trial package through Harbor:

```bash
# Dry run: check preflights and validate configuration
taskgo harbor run ./trial --dry-run

# Offline inspect: print resolved Harbor configuration
taskgo harbor run ./trial --print-config

# Live execution: launch container trial and collect outputs
taskgo harbor run ./trial -o ./results
```

### Execution Bounds Enforced by Default

- **Attempts:** Exactly 1 attempt (`n_attempts: 1`, `max_retries: 0`).
- **Concurrency:** Single worker (`n_concurrent_trials: 1`).
- **Timeouts:** 60s agent execution timeout, 180s setup timeout.
- **Network Egress:** Restricted to model endpoints
  (`generativelanguage.googleapis.com`).
- **Teardown:** Containers and transient networks deleted upon completion
  (`delete: true`).

## Candidate Verification (`taskgo harbor verify`)

The `verify` command runs deterministic host checks across candidate outputs,
evaluates findings against the 4 evaluation layers without invoking an LLM, and
compiles the Candidate Acceptance Packet.

```bash
taskgo harbor verify \
  --base-file ./fixtures/config.json \
  --candidate-file ./results/config.json \
  --completion-json ./results/completion.json \
  --result-json ./results/result.json \
  --tool-cmd "skills/coding-standards/scripts/json-format" \
  --task-id TASK-3A91F \
  --task-title "Format configuration" \
  -o ./acceptance-packet
```

### Verification Checks

1. **SHA-256 Hashes:** Computed for base file, candidate file, and patch.
1. **Patch Application:** Evaluates `patch --dry-run` to ensure clean
   application against the original base file.
1. **Syntax Validation:** Verifies valid JSON, YAML, or UTF-8 text encoding.
1. **Host Tool Rerun:** Runs specified host verification commands (`--tool-cmd`)
   on the base file and compares output hashes against candidate artifacts.
1. **Worker Claims Audit:** Extracts self-reported status and modified files
   from `completion.json`.

### Candidate Acceptance Packet Outputs

- `acceptance-packet.json`: Machine-readable packet for automated audit
  pipelines.
- `acceptance-packet.md`: Human-readable review document containing artifact
  digests, layer evaluations, advisory findings, unified diff, and acceptance
  recommendation.

### Output Verdicts

- **`READY_FOR_HUMAN_ACCEPTANCE`**: All independent host checks passed.
  Candidate is corroborated and ready for human review and sign-off.
- **`REJECT_OR_REPAIR`**: Independent checks failed (syntax defect, patch
  rejection, or tool discrepancy). Integration must not proceed.

## Bounded Repair Loops

When candidate outputs fail verification, a repair attempt may be initiated
under strict bounding policies:

1. **Maximum 1 Repair Attempt:** Unbounded retry loops risk billing runaway and
   prompt degradation.
1. **Deterministic Gate Priority:** Reviewer praise cannot override a failed
   negative gate (`patch --dry-run` or syntax failure).
1. **Trace Preservation:** Intermediate outputs and reviewer critiques must be
   preserved for post-mortem analysis.
